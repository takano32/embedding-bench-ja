# 方法と判断の記録

2026-11-02 に、nilkani06 の長期記憶（Hindsight の bank `nilkani06`）を使って、bge-m3 と Sarashina（`sarashina3-embedding`）を比べた。
この文書は手順と、その場で決めたことの理由を書く。数字は `results/summary.md`。私的な内容（記憶の本文、問い）は `data/` の中にだけあり、ここにも `results/` にもコミットメッセージにも書かない。

## 何を測るか

1. 実際の記憶で、正解が上位に来るか（正解1位率、上位 k 位の再現率、MRR、遅延）
2. いまの足切り（Hindsight 側 `SEMANTIC_MIN_SIMILARITY` 0.70、フックの `CANDIDATE_MIN_SEMANTIC` 0.70 と `MIN_SEMANTIC` 0.74）が、必要な記憶を落としていないか。関係あり／なしの類似度の分布と、値ごとの取りこぼしと混入

足切りの値は文書（`~/opt/hindsight-docker/standby/README.md`、`nilkani06/.agents/skills/memory/hindsight/SKILL.md`）に加えて、実物でも確かめた。
動いている `hindsight` コンテナの環境変数（`docker inspect` の `Config.Env`、読むだけ。値に鍵が混じるので足切りと埋め込みの設定だけを grep した）が `HINDSIGHT_API_SEMANTIC_MIN_SIMILARITY=0.70`、`HINDSIGHT_API_GRAPH_SEED_MIN_SIMILARITY=0.70`、`HINDSIGHT_API_SEMANTIC_LINK_MIN_SIMILARITY=0.88`、埋め込みは `sarashina3-embedding`（接頭辞 `[[sarashina:query]]`／`[[sarashina:document]]`）。
受信時のフック `nilkani06/scripts/hindsight-recall-hook.py` の定数は `CANDIDATE_MIN_SEMANTIC = 0.70`（Jev に回す候補の床）、`MIN_SEMANTIC = 0.74`（Jev が使えないときの戻り先）、`MAX_QUERY_CHARS = 500`。
同じ環境変数に、リランカーが `cohere`（`sarashina3-rerank`、候補の上限 80、タイムアウト 2 秒、失敗時は rrf）とある。**本番の recall はこのリランカーを通る**が、ここでは通していない（下の「測っていないこと」）。

## 対象

- bank `nilkani06` の全記憶 9,676 件（world、experience、observation）。bank `zerozari00` は使っていない。
- 記憶のベクトルは本番が保持しているものをそのまま読んだ。Sarashina は `memory_units.embedding`、bge-m3 は控えの表 `memory_units_standby`（`model='bge-m3'`）。どちらも、本番の retain と同じ形（本文に日付と実体名を足した文）を埋め込んだもの。接頭辞は Sarashina が `[[sarashina:document]]`。
  文書側を撃ち直さないので、Sarashina の枠は問いの 200 回と抜き取り検査の 24 回しか使っていない。
- 両方のベクトルを持たない記憶（控えが未充填）は除いた（本番にあった 9,679 件のうち 3 件）。
- 問いの埋め込みは自分で撃った。Sarashina は `[[sarashina:query]]` を付け、bge-m3 は接頭辞なし（本番と同じ）。
- 全記憶を総当たりのコサインで順位づけた。本番の recall は意味検索のほかに全文検索、グラフ、リランカーを混ぜるので、ここで測るのは「埋め込みだけで引いたときの順位」で、本番の受信時の挙動そのものではない。
- 本番は受信したチャンネルで記憶を絞る（管理チャンネル以外は `chat:<id>` と `scope:global` の印のもの）が、ここでは絞らない（管理チャンネルからの検索と同じ条件）。

## 問い 200 問

| 種別 | 数 | 作り方 | 正解の意味 |
|---|---|---|---|
| K（既知の1件） | 116 | 乱数で抜いた記憶（seed）を読み、その事実を尋ねる問いと答えの要点を、本流（Claude）が書いた。`d`＝元の文と語を共有する言い方 59 問、`i`＝言い換え・遠回しな言い方 57 問 | 問いに答える事実を述べている記憶（seed 自身を含む。ほかにも同じ事実を述べる記憶があれば関連あり） |
| T（実メッセージ） | 84 | 本番の受信（takano32 の発言を取り込んだ文書）から乱数で引き、本文の先頭 500 字をそのまま問いにした | 本番のフックと同じ基準。同じ話題・人・案件・前の決定に関わり、思い出すと理解や返答の助けになる記憶 |

### 問いの作り方の偏り（結果を読むときの注意）

- K は seed の事実から書いた問いなので、元の文を見て作った分だけ、埋め込みに有利に出やすい。`d` は特に有利で、`i` は言い換えて有利さを減らしたつもりだが、完全には消えていない（書き手が元の文を読んでいる）。両方の数字を分けて出す。
- K は seed が「1件で答える事実」を持つ記憶に偏る（短い事実文、設定値、数字）。会話の雰囲気のような曖昧な記憶は seed に選ばなかった（聞き方が書けないため）。曖昧な記憶の検索は K では測れていない。
- T は元の文を見て作っていないので、この偏りがない。代わりに、正解が何件あるかが問いごとに違い、正解は「関連あり」の判定に依る（Jev の癖が出る）。受信が短い、指示語だけ、などの問いは正解が少なく、関連ありが 0 件の問いは指標から除いた。
- T の leave-one-out: その文書から作られた記憶、それを材料に含む observation、同じチャンネルで受信の 5 分前から 30 分後までに作られた記憶（その場の返信、続く発言）を対象から外した。本番で引くときには存在しないため。それでも「あとから作られた別の記憶」は残るので、本番の再現ではなく、いまの記憶全体に対する検索の質。
- seed の選び方: 受信由来 62、他の人の受信由来 18、返信由来 52、observation 28 の候補（第1回）と、受信由来 14、返信由来 60、observation 36（第2回）から、聞き方が書けるものを選んだ。選んだ数は上の 116 問で、候補から外したものの偏り（曖昧な記憶、定型の点検記録）は上のとおり。

## 正解の付け方

- 候補（プール）: 問いごとに、bge-m3 の上位 20、Sarashina の上位 20、字 bigram の BM25 の上位 10（第3の検索。プールを比べる 2 モデルだけで決めないため）、K は seed を必ず足した（平均 37 件）。
- 深いプール（足切りの分析用）: 上のプールだけでは、閾値より下にある関連ありの記憶が見えない（プールは両モデルの上位だけなので、閾値を下げても再現が 1.000 のまま動かない）。そこで各モデルの上位 100、BM25 の上位 10、seed を足し（平均約 160 件/問、全体 32,073 組）、Jev が 60 件ずつに分けて追加で判定した（1 回）。プールにも入る記憶は 2 回の平均を使う。これでも上位 100 の外の関連ありは数えていない。
- Jev（`nilkani06/scripts/judge.py`）: 候補全部を 1 リクエストに入れ、候補ごとの yesno の p を取る。候補の並びを変えて 2 回撃ち、p の平均が 0.5 以上を関連ありとした。K は答えの要点を添えて「答えの事実を述べているか」、T は本番のフックと同じ問いを使った。
- 人手: 32 問（K 16、T 16。乱数で選んだ）について、本流が読んで付けた。候補は各モデルの上位 8 と BM25 の上位 5、K は seed を足したもの（Jev のプールの部分集合）。候補の並びは乱数で、スコアも順位も見せない。基準は Jev に渡した問いと同じ。
- Jev と人手の一致率は 32 問の人手プールの組で数える（seed は両方で関連ありに固定しているので除く）。
- 指標は上位 k（k<=20）が全部ラベル付きになる範囲だけで計算する。プールにない記憶は「関連なし」扱いになるので、プールの外にある関連ありの記憶は数えていない（再現率は上限寄り）。

## 指標

- 正解1位率: 1 位が関連あり。上位 k 位再現率（hit@k）: 上位 k に関連ありが 1 件以上（k=3、5、10）。MRR: 最初の関連ありの順位の逆数（上位 20 まで）。K はさらに seed 自身の順位（seed@k、MRR）。
- 信頼区間: 問いでのブートストラップ 10,000 回（乱数は固定）。差は同じ再標本での Sarashina − bge-m3。
- 閾値の分析: 各閾値で、関連ありのうち残る割合（再現）、関連ありを 1 件でも落とす問いの割合、K で seed が残る割合、関連なしが通る数（混入）。関連あり／なしのコサインの分位点と AUC（閾値によらない分離の強さ）。

## 負荷と枠

- Sarashina は 20 回/分以下（最小間隔 3.2 秒）。遅延が 20 秒を超えるか HTTP エラーが出たらその場で止める作りにした。止まらなかった（結果は `results/summary.md`）。
- bge-m3 は直列で、load1 が 5 を超えたら待つ作りにした。
- キャッシュ: 問いの埋め込みは `data/emb_cache/` に保存し、再実行では撃ち直さない。
- 実行中の箱: 2 コア、本番（Hindsight、PostgreSQL、Honcho ほか）が同居。

## 本番に触っていないこと

- PostgreSQL は `docker exec ... psql` を `default_transaction_read_only=on` で SELECT だけに使った。書き込み、DDL、設定変更、コンテナの再起動はしていない。
- Hindsight の HTTP API と MCP は使っていない（記憶の書き込みはもちろん、recall も撃っていない）。
- Jev は `judge.py` 経由で撃った。`judge.py` が学習結果を `nilkani06/.agents/configs/judge-fit.json`（git 管理外）に書き込むので、それだけは更新されている。

## 足切りが引いた上位にどう効くかの見方（`floor_effect`）

全記憶をコサインで並べた上位 60（本番の recall が返す件数に近い深さ）と上位 12（Jev が使えないときの戻り先が出す件数）を取り、足切りに当たる件数と、当たったときの関連あり（Jev の深いラベル）の変化を数えた。本番の recall は全文検索・グラフ・リランカーも混ぜるので、これは「埋め込みのコサインだけで並べた場合」の近似。
